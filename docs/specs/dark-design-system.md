### Selected visual grammar and placement

The seven supplied sites were visually inspected on 2026-11-06. The selected [Zed](https://zed.dev/) view combines a dark framed composition, fine lines and local hatching; [Entire](https://entire.com/) uses restrained tonal depth and bounded landscape/technical presentations. Borrow precision and restraint, not their layouts, imagery, logos, fonts, product claims or source code. Reference appearance is time-dependent. No reference implementation or performance claim is inferred from these observations.

Use three complementary details, not a repeating menu of effects:

1. **Construction rails:** a pair of fine, neutral vertical rules follows the outer edges of each existing non-hero content shell. Homepage sections use the current 1440px shell; tool content uses its current 1120px shell, and the shared footer retains its own 1440px shell. Alignment follows those actual containers rather than one viewport-fixed grid. Segmented rails are intentional; do not bridge differing documentation/footer widths with diagonal connectors or force them into a new shared width. Rails must be visibly quieter than existing section dividers. Keep current content edges, gutters and widths unchanged.
2. **Hatched punctuation:** short, shallow diagonal strokes appear only at major transitions, not around every component. On home, place one accent in the existing blank separation before installation, one before principles and one before the footer. On tool pages, use one above the reference region and one at the document-to-footer transition; do not repeat it at each article heading. Use the same stroke language across routes, with shorter/quieter accents on documentation. These are fragments inside existing empty space, not full-width bars, new sections or additional scroll distance.
3. **Matte grain:** one fine, achromatic, nonanimated texture occupies the empty outer gutter lanes inside the rails. It never becomes a page-wide overlay. Leave a clear buffer between texture and the content edge so wrapped text, focus outlines and selectable code remain on their original grounds. Avoid conspicuous speckles, cloudy variation, moire and visible tile seams. No grain is applied to the hero, tool paintings/scrims, mastheads, reference contents, prose, principles text, footer copy, commands, code, controls or the dock.

On narrow layouts, retain the existing 900px stacking rules. At 600px and below, omit vertical rails and gutter grain rather than spend the small reading gutter on decoration; retain only short hatch accents within the existing blank transition spaces. Do not shrink type, change task order, add mobile-only panels or increase section spacing to make a motif fit. At increased text size, actual clear space takes priority: omit or shorten a decorative fragment if its exclusion zone cannot be maintained, without runtime measurement.

Rails, hatching and grain derive from the existing neutral palette; their decorative opacity may be lower than the meaningful Divider role. This is **not** permission to reduce the opacity/contrast of existing row dividers, control boundaries, text, selected markers or focus outlines. Apply decorative opacity locally, never to a content-bearing ancestor. Exact neutral opacity, hatch pitch/length and grain seed are reversible finishing choices, to be tuned together on rendered pages; their placement, exclusions and hierarchy are fixed by this design.

### Ownership, layering and failure behavior

The current `src/styles/global.css` owns Canvas, `.shell`, `.doc-shell`, section spacing, responsive rules and forced-color accommodations. `ToolGrid.tsx` already separates `#tools` and the unfiltered `#install`; `ManifestoSection.astro` owns `#philosophy`; `Footer.astro` owns the shared footer; the single `src/pages/tools/[id].astro` template owns both tool routes. Extend those existing presentation owners rather than introduce a background provider, theme engine, React decoration island or second layout system.

Prefer CSS decoration on explicitly selected existing shell/section owners. A local class hook or nonsemantic, hidden decoration element is permitted only when needed to express a bounded region clearly. Do not apply an unqualified decoration rule to every `.shell`, `main`, `body` or every pseudo-element: nested shells and the full-bleed hero must not receive duplicate or inherited effects. The occupied `::before` layers on `.tool-feature` and `.doc-feature` protect the paintings' text contrast and remain unchanged. Do not reuse those layers, add grain to them or attach viewport-sized textures to their ancestors.

Use native static CSS for rails/hatching and a single small static monochrome grain tile, either CSS-embedded or repository-local. The tile's final embedded payload or local encoded file must be at most 8192 bytes and reused across all routes; no image-generation service, new dependency, browser-side random generation, animated SVG/filter, full-page filter pass, canvas, WebGL, observer, timer or event listener is justified. A local PNG tile may be generated offline during a separately authorized implementation; no generation occurs in this design phase. Do not add a runtime texture fetch API, preload, font, site setting or intensity control. Static texture is the bounded cost of this direction; a live material effect adds rendering/lifecycle complexity without serving the requested outcome.

Decorative layers must not participate in layout, hit testing, text selection, the accessibility tree, heading/contents generation or keyboard navigation. Keep them behind useful content and within their intended blank regions without clipping content or focus. Do not put opacity, transforms, filtering, isolation, containment, overflow clipping or a new z-index on a shared ancestor of the hero, dock or sticky reference contents. Such ancestor changes could alter sticky/fixed positioning or visibility even when the hero/navigation source bytes remain untouched. No `overflow-x: hidden` workaround is permitted.

Missing, blocked or unsupported texture leaves the same solid Canvas ground and working content. Initial HTML, no-JavaScript use and existing hydration boundaries remain unchanged. In forced colors, suppress **all new decoration**, retaining the existing native-aware meaningful boundaries and focus states; do not opt out of system colors. Reduced motion adds no special animation branch because the new decoration is static. Unsupported decorative styling may disappear without requiring a polyfill, browser sniffing or a replacement label. Normal image/font/copy/terminal failures retain their existing owners and behavior.
